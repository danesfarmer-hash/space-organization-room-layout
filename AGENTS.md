# Space Organization coding instructions

1. Read `docs/SPACE_ORGANIZATION_RULES.md` before changing this repository. For a consequential change, read the current private Global Rules working agreement when the user supplies access in the active chat. This repository does not contain that document, and a prior chat link is not loaded automatically.
2. Identify the current branch, commit, Pages source, and active build before editing. `index.html` is the deployed entry point on `main` as of the baseline recorded in the rulebook. It embeds Room Layout and Closet Builder; the two standalone HTML files are not automatically the deployed modules. Verify again each task.
3. Fill out `docs/CHANGE_CONTRACT.md` for each app change. Map acceptance criteria to rule IDs; identify affected and preserved behavior. Resolve material conflicts and missing geometry before coding. Do not alter unrelated icons, styling, or project data.
4. Keep one authoritative owner of the active build. Preserve a recoverable commit. Do not claim a code edit proves an interaction. Run `npm test`, then record all ten gates in `docs/RELEASE_CHECKLIST.md` and complete the relevant `docs/SMOKE_TEST.md` browser checks before claiming a release. Model geometry and 3D visibility are separate gates.
5. Report each criterion as PASS, FAIL, or NOT TESTED, with the exact commit, browser/viewport, visual evidence for geometry, persistence/reload result, and limitations. A failed required check blocks a release claim. Latest explicit user instructions control over older project defaults; surface conflicts.
